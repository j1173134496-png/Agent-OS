## 1. 文档目的

V0.3.2 已经完成原生智能体市场、Skill、MCP 工具声明和员工权限模型的架构接入，但当前运行结果证明“能展示”与“能使用”之间仍存在断层。

本任务书用于完成以下目标：

- 让“智能填报助手”从市场卡片变成真正可运行的公司 Agent。
- 让 Submit Flow 以独立、可启动、可监控、可恢复的服务形式运行。
- 让 AgentOS 能真实连接 Submit MCP 并加载七个受控工具。
- 让市场启动链路稳定保留 `agent_id=smart-submit-v1`，不回退到普通文本模型。
- 修复消息一直转圈、没有有效 `streamId`、失败无明确提示的问题。
- 完成站点、月份、附件、任务、人工复核和产物下载的真实业务闭环。
- 把身份、权限、密钥、附件、任务和产物隔离落实到服务端。
- 重写 Gate，使“运行可用”成为发布条件，而不是只检查数据库字段和静态文件。
- 形成可追溯、可重复、可回滚的 V0.3.3 发布记录。

本轮不是重新设计智能体市场，也不是扩展新的业务 Agent。核心任务是把现有 V0.3.2 架构补齐为可用产品。

## 3. 根因判断

当前不可用不是单一故障，而是三层问题叠加。

### 3.1 第一层：市场启动链路没有被真实验收

用户截图中的会话仍是普通文本模型，说明该次操作没有形成有效 Agent 会话。可能原因包括：

- 用户只打开卡片或返回旧会话，没有完成“开始对话”。
- 旧前端缓存仍使用修复前的路由逻辑。
- `agent_id` 在 URL 参数归一化、新会话模板或状态恢复阶段被普通模型规格覆盖。
- 页面虽然短暂进入 Agent，但刷新、跳转或创建 Conversation 时回退为普通模型。

本层不能仅靠源码静态断言验收，必须用浏览器和数据库共同验证。

### 3.2 第二层：Submit MCP 运行服务缺失

AgentOS 配置声明了 Submit MCP，但没有任何受管理进程实际监听 8121 端口。因此：

- AgentOS 启动时无法初始化 MCP。
- 七个工具只存在于发布清单和数据库声明中。
- Agent Runtime 实际获得零个 Submit 工具。
- 即使 Agent 会话路由正确，也无法执行智能填报工作流。

这是当前功能不可用的直接阻塞项。

### 3.3 第三层：生成任务和错误反馈没有闭环

用户页面持续加载，对应日志出现：

```text
[AgentStream] Job not found for streamId: undefined
```

这说明至少存在以下一种情况：

- 生成启动请求没有返回合法 `streamId`。
- 前端在请求失败后仍进入等待/终止逻辑。
- 路由回退导致请求发送到错误 Endpoint。
- 后端失败响应没有被前端转成可见错误。

该问题必须通过浏览器 Network 证据或等价的受控 E2E 捕获请求与响应，不允许仅根据单条日志猜测。

### 3.4 管理根因：Gate 把“配置存在”误判成“功能可用”

V0.3.2 Gate 缺少真实依赖、真实协议、真实会话和真实业务验收，因此无法阻止一个零工具 Agent 被发布。这是本轮必须修正的工程管理问题。

## 4. 目标架构

```text
员工浏览器
  -> AgentOS 智能体市场
  -> 智能填报助手 smart-submit-v1
  -> LibreChat Agent Runtime
  -> 服务端可信身份/策略上下文
  -> Submit Streamable HTTP MCP
  -> Submit Task Service / Worker / OCR / Excel
  -> task / review / artifact 结构化结果
  -> AgentOS 对话和授权下载
```

### 4.1 所有权边界

| 范围 | AgentOS 负责 | Submit Flow 负责 |
|---|---|---|
| 用户与角色 | 登录、用户、角色、市场使用权限 | 只信任经过验证的服务端上下文 |
| 会话 | Conversation、Message、Agent 路由、流式响应 | 保存与业务任务关联的会话标识 |
| Agent | 发布、版本、Skill/Tool 白名单、模型与推理策略 | 校验请求是否来自允许的 Agent 版本 |
| 附件 | 接收上传、生成不透明附件 ID、传递授权引用 | 校验附件归属、复制/读取受控文件 |
| 业务任务 | 展示状态、发起工具调用 | `task_id`、状态机、OCR、校验、复核、Excel |
| 产物 | 展示下载入口 | 生成产物、索引、哈希、授权读取 |
| 审计 | 用户、会话、Agent 和调用审计 | 业务状态变化、复核和产物审计 |

### 4.2 禁止的架构

- AgentOS 前端直接调用 Submit CLI。
- LLM 参数包含本地路径、任意 URL、Shell、Python、SQL 或自由命令。
- 把任务状态只保存在聊天消息中。
- 使用客户端可伪造 Header 作为最终授权依据。
- 用 30 分钟同步 HTTP/MCP 请求承载完整 OCR 和 Excel 流程。
- 直接向用户暴露 Submit 服务器本地文件路径。
- 让普通模型会话直接调用隐藏的 Submit MCP。

## 8. 阶段 1：把 Submit MCP 建成可管理服务

### 8.1 目标

消除“只有手工脚本、没有运行服务”的直接阻塞，使 Submit MCP 可启动、可检查、可恢复、可固定版本。

### 8.2 服务归属决策

Submit MCP 仍由 `K:\Workers\Submit_Flow_Agent` 拥有。推荐实施方式：

- 在 Submit 仓库内提供 Dockerfile、Compose 或等价受管理服务定义。
- 生成独立、不可变的 Submit MCP 镜像。
- 通过稳定内部网络地址向 AgentOS 提供服务。
- AgentOS 只保存服务 URL 和环境变量引用，不挂载 Submit 源码。

开发机可以暂时使用 `host.docker.internal:8121`，但正式部署必须使用明确的内部 DNS、容器网络或服务发现地址，不得依赖某个开发人员手工打开 PowerShell 窗口。

### 8.3 必做任务

| ID | 任务 | 实施要求 |
|---|---|---|
| AOS-033-01-01 | 增加 Submit MCP 服务定义 | 独立进程、固定入口、固定端口、非 root 优先 |
| AOS-033-01-02 | 增加 `/healthz` | 只表示进程存活，不泄露配置 |
| AOS-033-01-03 | 增加 `/readyz` | 验证配置、运行目录、必要依赖和任务存储可用 |
| AOS-033-01-04 | 增加自动重启 | 进程异常退出后自动恢复，避免重启风暴 |
| AOS-033-01-05 | 增加结构化启动日志 | 记录版本、监听地址、协议版本和就绪状态，不记录秘密 |
| AOS-033-01-06 | 固定镜像 digest | Release Record 必须引用 digest，不允许正式环境使用浮动 tag |
| AOS-033-01-07 | 增加一键本地编排入口 | 明确启动 Submit、检查就绪、再启动 AgentOS 的顺序 |

### 8.4 配置要求

SUBMIT_AGENT_VERSION

规则：

- `.env.example` 只写占位符。
- `.env` 不进入 Git。
- 运行配置只引用 `${SUBMIT_MCP_TOKEN}`，不得展开真实值写入 YAML。
- 已经在早期调试中暴露过的服务 Token 必须在受控维护窗口轮换。
- Token 轮换必须同时验证旧 Token 失效和新 Token 生效。

## 9. 阶段 2：完成真实 MCP 协议和七工具发现

### 9.1 目标

让 AgentOS 在运行时真实初始化 Submit MCP，并发现七个工具，而不是只在 MongoDB 里声明工具名称。

### 9.2 协议要求

## 14. 阶段 7：把长任务改为异步状态机

### 14.1 目标

取消 30 分钟同步 MCP 请求，避免 OCR、Excel 或人工复核长期占用 LLM 工具连接。

### 14.2 目标语义

- 创建/启动操作在短时间内返回 `task_id` 和当前状态。
- Worker 在后台推进确定性任务。
- Agent 使用 `get_task` 查询状态。
- 人工复核使用独立确认操作。
- 客户端断线不会取消业务任务。
- 重试不会重复创建任务或重复生成产物。

### 14.3 工具兼容策略

V0.3.3 可保留 `submit_flow.run_task` 名称以兼容已发布 Agent，但语义应调整为“排队/启动任务并快速返回”。若必须新增 `start_task`，需要：

- 更新 MCP 合同。
- 更新原生工具注册表。
- 更新 Agent 版本和 Skill。
- 明确兼容和弃用策略。
- 重新完成全部 Gate。

执行 AI 不得只修改工具名而不更新合同、Agent 和测试。

### 14.4 状态建议

```text
draft
collecting_files
ready_to_run
queued
running
need_review
completed
failed
cancelled
```

### 14.5 阶段 Gate

- 启动任务在规定短超时内返回。
- 长任务执行期间 AgentOS 请求连接已释放。
- 轮询、重试、断线恢复和服务重启测试通过。
- 同一幂等键不会产生重复任务或重复产物。
- `deployment/librechat.yaml` 不再使用 30 分钟超时掩盖同步执行。

## 20. 完成定义

只有以下条件全部满足，才可以向产品负责人报告“智能填报助手已经完成，可以验收”：

1. 从员工市场进入后显示的是“智能填报助手”，不是普通模型。
2. 持久化会话为 `endpoint=agents`、`agent_id=smart-submit-v1`。
3. Submit MCP 是受管理且 ready 的服务。
4. AgentOS 真实发现七个 Submit 工具。
5. 一次真实消息获得有效 `streamId` 并完成响应。
6. Submit 不可用时页面明确报错，不无限加载。
7. 成功、复核、失败和重复提交业务路径全部验证。
8. 普通聊天、其他用户和其他会话无法越权。
9. 长任务采用异步语义，不占用 30 分钟 MCP 请求。
10. 单元、集成、浏览器 E2E、全量回归和回滚演练全部通过。
11. 所有证据由最终代码、最终配置和最终镜像重新生成。
12. V0.3.3 Release Record 包含 Git 基线、镜像 digest、配置哈希、测试摘要、已知问题和审批人。
13. 总 Gate 中没有 `FAIL`、`BLOCKED`、`DEFERRED` 或 `NOT_RUN`。
14. 产品负责人完成最终体验验收并批准进入 V0.4。
